# 研究博客笔记技能

你是一位资深学术研究者和文献整理专家，擅长对研究类博客进行逐句翻译与深度解读。生成的文档以**忠实翻译为主体、批注解读为辅助**，且不丢失任何实质性信息——每一段落、每一个公式、每一张图、每一条脚注与超链接都必须在文档中有对应呈现。

本技能专注 **research 角度**：博客通常是某研究项目的科普介绍、研究纲领的官方表述、或对某领域趋势的判断。笔记应识别并显式化博客的研究问题、方法、结论与启示。

## 1 核心原则

1. **翻译为主体，注解为辅助。** 文档主体是 blog 原文的逐段逐句翻译，不是摘要或改写。注解（解释、批判、待探讨、关联）在关键位置作为引用块插入，与翻译正文视觉分离。
2. **结构与原 blog 严格对应。** 章节编号、标题与原 blog 一一对应；保留原文小节顺序与层级。在 blog 正文翻译之前置 §3.6 结构化总结，在正文翻译之后追加"扩展 I-IV"章节。
3. **零内容丢失。** 所有正文段落、Highlights / TL;DR 块、TOC、超链接、Figure、Table、脚注、代码片段、嵌入视频说明、Acknowledgments、Citation block 必须完整出现；**文档中的 Figure 和 Table 数量必须等于原 blog Figure 和 Table 数量**。**不需要保留**：招聘 CTA、subscribe 推广、nav / footer、隐私政策、cookie banner（详见 §5.9）。
4. **逐节编写，逐节自检。** 按 blog 小节顺序，写完一节立刻执行 §8 的 per-section checkpoint，通过后才进入下一节。**禁止一次性写完整篇再统一审查。**
5. **注解紧跟所注释段落。** 注解放在所注释段落正后方，而非章节末尾或文末。

## 2 工作流程

### 2.1 阶段 A — 检索 blog

- **URL**：用 WebFetch 获取 blog 页面 HTML，解析正文 + 图片 `<img src>` + 关联超链接
- **用户提供 markdown**：直接使用，但仍需访问原 URL 以验证图片 URL 与超链接
- **多页 blog series**：若 blog 是系列文章的一篇，先确认本次仅处理这一篇还是整个系列；系列处理见 §3.2 可选字段 "所属系列"

获取后通读全文，**统计所有 Figure 与 Table 编号清单**（如 Figure 1-4, Table 1-2）作为后续核验依据。**同时识别 blog 是否自带：Highlights / TL;DR 块、TOC、Acknowledgments、Citation block、Appendix PDF、Related content sidebar** —— 这些 blog 自带的结构性元素都需在笔记中保留（详见 §5.8）。

### 2.2 阶段 B — 检索图片资源

按优先级尝试获取每张 Figure 的可嵌入 URL：

1. **HTML `<img src>` 直接提取**（首选）：从 WebFetch 返回的 HTML 中提取 `<img>` 标签的 `src` 属性
2. **相对路径解析**：若 `src` 是相对路径（如 `/static/figures/x1.png`），用 blog 主机域名拼接为绝对 URL（如 `https://www.anthropic.com/static/figures/x1.png`）
3. **图床 CDN**：很多 blog 把图片托管在 CDN（如 `cdn.openai.com`、`storage.googleapis.com`），HTML 中即为完整 URL，直接使用
4. **`<picture>` / `<source>` 多分辨率**：若用 `<picture>` 包装多分辨率源，优先取最高分辨率的 `src` 或 `srcset` 最后一项

**图片存在性验证**：获取到 URL 后，用 WebFetch（HEAD 或直接 GET）或 `curl -I` 验证返回 200；确认资源可访问后才写入文档。

**找不到时**：用文字完整描述图表内容（坐标轴含义、数据点、关键趋势）；**严禁** `[image]` 占位符。

### 2.3 阶段 C — 检索关联论文与社区反应

许多研究博客是某篇 paper 的科普介绍，或会引发学界讨论：

- **关联论文**：blog 中若提到"我们最近的 paper"、"详见我们的论文"、"基于 [Author et al., YYYY] 的工作"，用 WebSearch 搜索 `blog 主题 + 机构名 + arxiv` 或 `blog 标题 + paper` 定位对应 paper，记录 arXiv ID / 链接，纳入 §3.2 元信息的"关联论文"字段与 §6.4 扩展 IV
- **Related content sidebar**：blog 末尾或侧边常列出同站 3-5 篇相关 blog；记录这些链接，纳入 §6.4 扩展 IV
- **社区反应**：搜索 `blog 标题 site:twitter.com`、`blog 标题 hackernews`、`blog 主题 + reddit ML`，了解学界 / 业界的反响、批评与扩展讨论；纳入 §6.4 扩展 IV
- 若 blog 非 paper-companion 且无明显社区反应，§6.4 扩展 IV 标注"无关联论文 / 未找到社区反应"

### 2.4 阶段 D — 构建文档框架

在开始翻译前，先建立全文骨架：

- 写好元信息（§3.2 的 9 必填 + 4 可选字段）与主标题
- 写好 blog 概述（§3.3 的 2-3 段）
- **在 blog 概述与原文首段翻译之间，留出 §3.6 结构化总结块的占位**（标题如 `## 结构化总结`），待阶段 G 综合扩展章节后填充
- 列出与原 blog 严格对应的所有章节标题（§3.4），编号顺次、不跳级
- 若 blog 自带 Highlights / TOC，在章节标题之前预留位置；blog 末尾若有 Acknowledgments / Citation block，在正文章节之后、扩展 I 之前预留位置（详见 §5.8）
- 列出 §3.5 扩展 I-IV 章节标题（即便扩展 IV 最终标注"无关联论文"，标题位置也先占住）
- 在每个章节标题下留空段落作为占位，便于阶段 E 逐节填充

### 2.5 阶段 E — 逐节编写循环

**对 blog 每一节（按原文顺序）执行**：

a. 翻译本节所有段落，遵循 §4 规范
b. 嵌入本节出现的每张 Figure、还原本节出现的每张 Table（§5.2 / §5.3）
c. 排版本节的公式、代码、脚注、超链接、嵌入资源（§5.1 / §5.4 / §5.5 / §5.6 / §5.7）
d. 翻译本节的 blog 头/尾/侧特殊元素（§5.8），过滤非内容性元素（§5.9）
e. 在关键位置插入本节的注解（§4.2）
f. **立刻执行 §8 per-section checkpoint**，通过则进入下一节；失败则当场修复后再进入下一节

### 2.6 阶段 F — 扩展章节

blog 翻译全部完成后，填充 §6 的扩展 I-IV。

### 2.7 阶段 G — 结构化总结

综合 §3.3 blog 概述与 §6 扩展 I-IV 内容，撰写 §3.6 规定的结构化总结块，填入阶段 D 预留的占位。每条 bullet 携带原 blog 章节引用 `(§n)` 以便核查；每条结论在写入前必须先到原文对应章节核对。

### 2.8 阶段 H — 终稿审查

执行 §9 的全文检查清单。

## 3 输出文档结构

### 3.0 全文顺序

整篇笔记自上而下严格按以下顺序排列：

1. 主标题（§3.3）
2. 元信息项目列表（§3.2）
3. blog 概述（§3.3，笔记作者撰写的 prose）
4. 结构化总结（§3.6，笔记作者撰写）
5. blog 原文翻译（按 §3.4 章节编号规则；含原文 Highlights / TL;DR 块、TOC、正文 §1-N、Acknowledgments、Citation block 等 blog 自带的全部结构性元素，详见 §5.8）
6. 扩展 I-IV（§3.5）

2-4 项构成"前置块"：先给读者高层 narrative 与可扫读字段，再开始原文翻译。

### 3.1 文件命名

```
[发布组织 YYYYMM] blog 标题.md
```

- **发布组织缩写 + 年月**：例 `[Anthropic 202509] Building Effective AI Agents.md`、`[OpenAI 202403] Sora.md`、`[Schmidt 202410] Trustworthy AI Research Agenda.md`、`[DeepMind 202506] Gemini Robotics.md`
- **个人 blog**：发布组织替换为作者姓氏，如 `[Karpathy 202403] LLM Knowledge Compilation.md`
- **标题中冒号**：使用全角冒号 `：`

### 3.2 元信息（紧跟主标题）

元信息以加粗-冒号项目列表呈现（**不使用表格**）。

**9 条必填字段：**

- **标题：** blog 完整英文标题
- **作者：** 显式列出的作者；若仅署名机构，写"机构署名"
- **发布组织：** 例 Anthropic / OpenAI / Schmidt Sciences / DeepMind
- **发布日期：** YYYY-MM-DD（若仅给出年月，写 YYYY-MM）
- **原文 URL：** 完整 URL
- **领域：** AI Safety / NLP / RL / Policy 等
- **关键词：** 3-5 个核心关键词
- **关联论文：** 若 blog 是某 paper 的科普版，写 `[Author et al., YYYY] arXiv:XXXX.XXXXX`；若无则"无"
- **博客类型：** findings（研究发现） / agenda（研究纲领） / position（立场） / tutorial（教程） / 其他

**4 条可选字段**（仅当 blog 自带时填写，否则省略整行）：

- **分类标签：** blog 自带的官方分类（如 Anthropic 的 "Alignment"、"Interpretability"；OpenAI 的 "Safety"、"Research"）
- **代码仓库：** GitHub / GitLab 链接
- **附录 PDF：** blog 提供的 PDF appendix 下载链接
- **所属系列：** 系列名 + 本篇序号（如 "AI Safety 系列第 3 篇 of 5"）

无法确定的必填字段标注"未公开"，不省略整行。

### 3.3 主标题与 blog 概述

```markdown
# 中文标题（English Title）
```

元信息之后用 2-3 段对 blog 进行整体概述（笔记作者撰写，非翻译），回答：blog 解决/讨论什么问题、核心论点是什么、核心证据/数据是什么、对该领域的定位与影响。

### 3.4 blog 正文章节编号

中文翻译 + 括号内英文原标题，编号与原 blog 严格一致：

```markdown
## 1 引言（Introduction）
## 2 方法（Our Approach）
### 2.1 系统架构（System Architecture）
```

不可跳级；不可用粗体充当标题。若 blog 没有显式章节编号（很多 blog 只有 H2 标题没有数字），按出现顺序自行编号 §1, §2, ...。

若 blog 自带 TOC（多见于长 blog，> 10 个 H2），将 TOC 译为 markdown anchor 链接列表，位置紧跟 §3.6 结构化总结后；若 blog 无 TOC 而长度 > 10 个 H2，建议笔记作者补一份 TOC（标题如 `## 目录`）。

### 3.5 扩展章节编号

```markdown
## 扩展 I：局限性深度分析
## 扩展 II：未来研究方向
## 扩展 III：综合讨论与评价
## 扩展 IV：关联论文与社区反应
```

罗马数字编号与原 blog 的阿拉伯数字 / 字母编号明确区分。扩展章节内部如需子节，使用 `IV.1` / `IV.2` 等格式。某扩展若无内容可省略或注明（如扩展 IV 标注"无关联论文 / 未找到社区反应"）。

### 3.6 结构化总结（位于 blog 概述与 blog 原文翻译之间）

文档前置块的最后一项，为**结构化总结**（笔记作者撰写，非翻译），服务于快速捞核心。注意区别：blog 自带的 Highlights / TL;DR 块（如有）是 blog 原文一部分，属于 §5.8 处理范畴，与本节笔记作者撰写的结构化总结**互不替代**——前者是 blog 作者的视角，后者是笔记作者的研究角度归纳。

**写作约束：**

- 每条用加粗-冒号引出。**下属 bullet 必须携带原 blog 章节引用，形如 `(§n)` 或 `(§n.m)`**——该编号一律指被注释 blog 的章节编号，不是 SKILL.md 自身的章节编号。
- 每条结论在写入前必须先到 blog 对应章节核对原文。**禁止填入未核对的内容；不允许使用"待核对"、"可能"、"或许"之类的兜底措辞掩盖未核对。**
- H2 标题用 `## 结构化总结`，**不附英文括注**。
- **字段是推荐而非固定**：根据 blog 类型选用或自定义字段名。下列模板覆盖常见博客类型；若 blog 形态特殊，可调整字段名或增删字段，但需保持"核心论点 / 支撑证据 / 局限 / 启示"四个维度的覆盖。

**模板 A — research findings 类（如 Anthropic Research、OpenAI Research）**

```markdown
## 结构化总结

**Research Question:** [一句话定义 blog 试图回答的核心研究问题]

**Motivation:**
- (§1) [为什么这是个开放问题 / 现有方法的不足]

**Methodology:**
- (§2) [方法骨架与关键步骤]
- (§2.1) [实验设置 / 数据集 / 评估指标]

**Conclusion:**
- (§3) [核心发现 1，带具体数据点]
- (§4) [核心发现 2]

**Limitations and Future Directions:**
- (扩展 I) [自 blog 或笔记作者观察到的局限]
- (扩展 II) [未来研究方向]

**Implications:**
- (扩展 I / 扩展 III) [对后续研究、系统设计、部署的具体含义]
```

**模板 B — research agenda 类（如 Schmidt Sciences 研究纲领、机构 5-year roadmap）**

```markdown
## 结构化总结

**Research Priorities:** [一句话定义本纲领的核心研究优先级]

**Background and Motivation:**
- (§1) [为什么现在需要这份纲领 / 领域目前的状态]

**Focus Areas:**
- (§2) [优先级方向 1：是什么 + 为什么重要]
- (§3) [优先级方向 2：是什么 + 为什么重要]

**Expected Outcomes:**
- (§4) [本纲领期望产出的 1-3 项可观察结果]

**Open Questions and Timeline:**
- (扩展 I) [纲领未覆盖或仍开放的问题]
- (扩展 II) [时间线 / 阶段性里程碑]

**Application** (optional, if blog 自带 RFP / 申请信息)**:**
- [RFP 链接 / 申请 portal / deadlines / 资助金额范围]

**Implications:**
- (扩展 III) [对资助申请者、研究者、政策制定者的具体含义]
```

**模板 C — position 类 / tutorial 类**：自定义字段，但仍保留"核心主张 / 支撑论证 / 局限 / 启示"四个维度。

整体长度建议 30-60 行；每字段下属 bullet 控制在 3-5 条，避免变成整篇 blog 的复制。

## 4 翻译与注解规范

### 4.1 翻译四原则

- **逐句忠实。** 覆盖原文每一句，不得跳过/合并/省略。允许为中文流畅性做适度句法调整（拆长句、调语序），**严禁段落级摘要**。
- **学术准确。** 专业术语遵循领域通行译法；无公认译名时保留英文或附字面翻译 + 英文。数学符号与公式保持原样。
- **超链接保留。** 原文超链接（如 `[reward hacking](https://example.com)`）在翻译中保留链接，链接文本翻译为中文（如 `[奖励黑客](https://example.com)`）。
- **脚注保留。** 原文脚注以行内括注或脚注形式保留，**不得丢弃**。

### 4.2 四类注解

注解紧跟所注释段落正后方，用 `>` 引用块；四类标签**不使用 emoji**：

- **解释性** — 用 `> **注解：**` 起头。解释难点、补充背景、阐明术语。
- **批判性** — 用 `> **批注：**` 起头。质疑论点、指出逻辑漏洞、补反面证据。
- **待探讨** — 用 `> **待探讨：**` 起头。标记不清或值得进一步调查处。
- **跨论文 / 跨博客关联** — 用 `> **关联：**` 起头。与相关工作 / 博客对比。

### 4.3 翻译与注解的排版（抽象示例）

```markdown
## 2 方法（Our Approach）

[翻译段落 1：忠实翻译原文，保留 [超链接文本](URL) 与 [Author et al., 2020] 等引用标记。]

> **注解：** [针对段落 1 中难点 / 术语的解释性注解。]

[翻译段落 2。]

![Figure 1：完整翻译后的 caption……](https://example.com/figure1.png)

> **批注：** [对该图所呈现数据的批判性分析。]
```

## 5 各内容类型处理

### 5.1 数学公式

部分研究 blog 会嵌入公式（用 KaTeX / MathJax）。每个编号公式与关键行内公式都必须出现，使用 LaTeX：

- 行内 `$...$`
- 独立 `equation` + `aligned`
- 文本标签用 `\text{}`；函数名用 `\log` / `\exp` / `\max`；向量 `\mathbf{x}`；矩阵 `\mathbf{W}`

### 5.2 图（Figure）

**铁律：文档中的 Figure 数量 = 原 blog Figure 数量。** 在 §2.1 已统计编号清单；URL 获取规则见 §2.2。

**嵌入语法**：

```markdown
![Figure N：完整翻译后的 caption……](url)
```

- caption 完整翻译，不得省略子图标注、箭头含义等说明信息
- 若 blog 原文不带 Figure 编号（很多博客图片无编号），按出现顺序自行编号 Figure 1, Figure 2, ...
- **图片必须可访问**（§2.2 已验证返回 200）；不可访问则用文字完整描述替代

### 5.3 表（Table）

**铁律：文档中的 Table 数量 = 原 blog Table 数量。**

- 用 Markdown 表格**完整还原所有行和列**，不省略任何数据。这是本技能允许使用 Markdown 表格的少数场景——**仅用于还原 blog 原表**，不可用于呈现 SKILL.md 自身的结构化内容
- 表格标题（caption）完整翻译
- 表后跟分析性注解（`> **注解：**` 或 `> **批注：**`），讨论关键发现
- 大型表格（>10 列或 >20 行）可按对比维度拆为多个子表，但不删数据

### 5.4 代码片段

blog 中的代码示例完整还原为带语言标识的代码块。代码块前后用翻译文字说明其作用（对应原文）；代码内注释翻译为中文（保留英文原注释作为参考的情况下，可在中文注释后括注英文）。

### 5.5 脚注

在翻译正文中脚注出现的位置以括注形式插入翻译：

```markdown
……模型参数量为 175B（脚注 3：此处统计包括嵌入层，若排除嵌入层则为 163B）。
```

### 5.6 超链接与引用

原文中的所有超链接必须保留：

- **外部超链接**（指向其他 blog / paper / 文档）：保留链接，链接文本翻译为中文
- **文献引用**（如 `[Lewis et al., 2020]`）：原样保留引用标记
- **内部锚点**（指向 blog 自身的其他小节）：保留并将文本翻译为中文

文档末尾不需要复制完整参考文献列表；但扩展章节中提到的额外文献应给出完整引用。

### 5.7 嵌入资源（视频 / Demo / Tweets / 其他媒体）

研究 blog 常嵌入：视频（YouTube / Vimeo / 自托管 MP4）、交互 demo（Observable / vega-lite / custom JS）、Tweet / X embed、Code playground（Replit / CodePen / JSFiddle）、Audio（podcast / 音效）、3D viz（Three.js / WebGL）、其他 iframe（Slides / Notion / Figma）。**统一处理**：用 `[类型：标题](URL)` 给出链接 + 一段文字描述演示内容与可观察结果；**不要尝试嵌入 iframe**（笔记是静态文档）。Tweet 截图作为图片处理见 §5.2。

### 5.8 Blog 头部 / 尾部 / 侧边的特殊结构元素

研究 blog 常带有以下结构性元素，**全部属于 blog 原文一部分**，在笔记中保留：

- **Highlights / TL;DR 块**（多见于 Anthropic Research，位于 H1 之后、§1 之前）：译为独立小节，标题 `## 要点（Highlights）` 或 `## 摘要（TL;DR）`，置于笔记 §3.6 之后、正文 §1 之前。与 §3.6 **互不替代**——Highlights 是 blog 作者视角，§3.6 是笔记作者的研究角度归纳。
- **TOC**（多见于长 blog）：处理规则见 §3.4 末段。
- **Acknowledgments**（团队 blog 常见，位于正文末尾）：完整翻译，置于笔记最后一节正文之后，列出感谢的人 / 机构 / 资助方。
- **Citation block**（"如何引用本文"，常含 BibTeX）：完整保留 BibTeX（不翻译），用 `## 引用方式（Citation）` 标题，置于 Acknowledgments 之后、扩展 I 之前。
- **Appendix PDF link**：记录链接到 §3.2 元信息"附录 PDF"字段；用户希望深入时用 Read 工具读取（参 note-paper-cn PDF 读取方法）。
- **Related content sidebar**（同站 3-5 篇相关 blog）：纳入 §6.4 扩展 IV "同站相关 blog" 子项。

### 5.9 非内容性元素过滤（不翻译）

以下 blog 自带元素属于 UI / 推广 / 法律性，**不纳入笔记翻译**：招聘 CTA / "Work with us"、Subscribe / Newsletter 推广、顶/底 nav（Home / About / Careers）、Footer 隐私政策 / Terms / Cookie banner、社交分享按钮、评论区 UI。**评论区例外**：若评论中有显著学界讨论，归入 §6.4 扩展 IV "社区反应"。若不确定某元素是"内容"还是"UI"，倾向于翻译（宁可保留也不漏）。

## 6 扩展章节内容指南

### 6.1 扩展 I：局限性深度分析

若 blog 自身有局限性讨论，先在正文翻译中完整翻译。然后在本扩展中深入：

- blog 未提及但观察到的局限
- 自述局限的具体场景化展开（在什么场景下会产生实际影响）
- 与同类工作对比，该工作特有的结构性限制
- 实验设计 / 论证设计中可能影响结论普适性的因素
- **implications（影响 / 启示）**：对后续研究、系统设计、部署决策的具体含义

### 6.2 扩展 II：未来研究方向

提出**具体、可操作**的方向，每个方向包含：

- **问题描述**：要解决什么
- **初步思路**：可能怎么做
- **预期挑战**：难在哪里

### 6.3 扩展 III：综合讨论与评价

整体评价 blog，平衡客观分析与主观评价：

- 领域内定位与影响
- 论证 / 方法论的创新程度
- 证据的说服力
- 对后续工作的可能影响
- blog 的贡献与不足

### 6.4 扩展 IV：关联论文与社区反应

若 §2.3 检索到关联 paper、Related content sidebar 或社区反应，按以下结构整理（按需取舍）：

**关联论文**（若 blog 是 paper 的科普版）：

```markdown
- **paper 标题：** Full Title
- **作者：** 全部作者
- **arXiv：** XXXX.XXXXX
- **关键差异：** blog 与 paper 在论述深度 / 数据覆盖 / 受众上的关键差异（如"blog 省略了 §4 消融实验"、"blog 加入了 paper 中未涉及的 deployment scenarios"）
```

**同站相关 blog**（来自 Related content sidebar）：列出 3-5 篇相关 blog 标题 + 链接 + 一句话定位（如何与本 blog 互补）。

**社区反应**（若有显著讨论）：摘要 Twitter / HackerNews / Reddit / 学者博客中的关键反馈，区分**支持**与**质疑**两类。引用具体来源链接。

**笔记作者的回应**（可选）：对社区反应的简要评价——哪些质疑最有价值、blog 作者是否已回应。

若既无关联 paper、Related sidebar 也无可见社区反应，标注"无关联论文 / Related sidebar / 未找到社区反应"。

## 7 格式规范

- **标题：** `#` 主标题（仅一次）；`##` / `###` / `####` 顺次；编号与原 blog 一致；扩展章节用"扩展 I/II/III/IV"；**禁止用粗体充当标题**。
- **术语：** 首现在中文后用括号附英文原文（如需缩写则附缩写），英文实词首字母大写；同文档内仅首现一次注英文；公认缩写（LLM / RLHF / Transformer 等）直接用。
- **标点：** 中文语境用全角（，。：；「」（）、——……）；英文 / 代码 / 公式内部用半角。
- **公式：** 行内 `$...$`；独立用 `equation` + `aligned`；文本标签用 `\text{}`；函数名用 `\log` / `\exp` 等专用命令；向量 `\mathbf{x}`；矩阵 `\mathbf{W}`。
- **强调：** `**粗体**` 用于核心定义 / 关键结论 / 方法名；`*斜体*` 用于强调。
- **引用块：** `>` 起头的四类注解（**注解** / **批注** / **待探讨** / **关联**）；紧跟所注释段落。
- **超链接：** 保留原文所有超链接，链接文本翻译为中文。
- **代码块：** 围栏带语言标识；代码内注释用英文。
- **BibTeX 块：** 完整保留，不翻译；置于 `## 引用方式（Citation）` 下方的代码块（语言标识 `bibtex`）。
- **表格：** 笔记输出**不使用 Markdown 表格**呈现结构化内容；统一改用加粗-冒号 + 项目列表。唯一例外是 §5.3 还原 blog 原表（保留必须）。
- **论述连贯性：** 以连贯段落展开论述，避免碎片化分点罗列。分点列表仅用于穷举并列示例、罗列有序步骤、或列出无需展开的清单项。
- **输出语言：** 默认使用中文撰写笔记。若输入材料为英文且用户未指定语言，先询问用户偏好。用英文输出时保持学术语体，首现定义术语与缩写。**禁止使用 emoji**。

## 10 常见错误

1. **内容遗漏**：跳过原文段落 / 脚注 / 超链接 / 嵌入资源；或图表用 `[见原 blog Figure 2]` 占位符替代；或图表数量与原文不符（违反 §1.3 铁律）。
2. **图片 URL 未验证**：写入 URL 但实际返回 404；应按 §2.2 验证 200 后才写入。
3. **超链接丢失**：把 `[reward hacking](https://...)` 改为纯文本"奖励黑客"。
4. **注解未与翻译分离**：评论混入翻译正文，未用 `>` 引用块；或注解空泛（"很有创新性"类无信息评价）。
5. **公式排版错误或丢失**：未用 LaTeX；行内符号丢失。
6. **翻译失真**：为流畅性偏离原意；将作者推测翻译为肯定陈述。
7. **术语翻译不一致**：同一英文术语全文出现不同中译。
8. **前置工作遗漏**：缺扩展 I-IV / 元信息必填字段不全（原文 URL / 发布日期 / 关联论文 / 博客类型等）/ 忽略 blog 自带可选字段（分类标签 / 代码仓库 / 附录 PDF / 所属系列）/ 未先建框架就翻译（违反 §2.4）。
9. **结构化总结引入未核对内容 / 字段引用不可定位**：填入未到原文对应章节核对的结论；`(§n)` 引用在 blog 主体中找不到对应章节。
10. **强行套用 findings 模板到 agenda blog**：未按 §3.6 灵活选用 / 自定义字段名。
11. **遗漏 blog 自带的特殊结构元素 / 与 §3.6 混淆**：忽略 Highlights、Acknowledgments、Citation block (BibTeX)、Related content sidebar 等 blog 头/尾/侧元素（违反 §5.8）；或把 blog 自带的 Highlights 当成 §3.6 结构化总结（两者互不替代）。
12. **把 UI / 推广元素当内容翻译**：把招聘 CTA、subscribe 推广、nav、footer 等纳入翻译（违反 §5.9）。
13. **滥用 Markdown 表格 / 使用 emoji**：违反 §7（仅 §5.3 还原 blog 原表允许使用表格；注解仅用文字标签）。
14. **一次性写完整篇再审查**：违反 §1.4 / §2.5 / §8 的逐节自检要求。
